# 代码审查检查清单

## 概述

本文档提供代码审查的全面检查清单，确保代码质量、安全性和可维护性。审查者应根据项目类型和代码复杂度适当调整检查标准。

## 审查流程

### 1. 准备阶段

- [ ] **理解上下文**
  - [ ] 阅读相关的用户故事和需求文档
  - [ ] 了解代码变更的业务目的
  - [ ] 检查相关技术文档和架构设计

- [ ] **环境准备**
  - [ ] 本地环境能够成功构建和运行
  - [ ] 所有测试通过
  - [ ] 代码格式化工具已运行

- [ ] **变更范围确认**
  - [ ] 确认变更的影响范围
  - [ ] 识别相关的模块和依赖
  - [ ] 检查是否需要更新文档

### 2. 代码质量检查

#### 2.1 代码结构和组织

- [ ] **文件结构**
  - [ ] 文件命名符合项目约定
  - [ ] 目录结构清晰合理
  - [ ] 文件大小适中（通常不超过500行）
  - [ ] 相关功能组织在同一模块中

- [ ] **类和函数设计**
  - [ ] 单一职责原则（SRP）
  - [ ] 开放封闭原则（OCP）
  - [ ] 依赖倒置原则（DIP）
  - [ ] 接口隔离原则（ISP）
  - [ ] 类和函数的职责明确
  - [ ] 抽象层次合理

- [ ] **代码复杂度**
  - [ ] 圈复杂度控制在合理范围（<10）
  - [ ] 避免深度嵌套（<3层）
  - [ ] 函数长度适中（<50行）
  - [ ] 参数数量合理（<5个）

#### 2.2 命名规范

- [ ] **变量命名**
  - [ ] 名称具有描述性
  - [ ] 避免缩写（除非是通用缩写）
  - [ ] 使用一致的命名约定
  - [ ] 避免使用单字母变量（除循环计数器）

- [ ] **函数命名**
  - [ ] 动词开头，描述功能
  - [ ] 返回值类型可从名称推断
  - [ ] 避免误导性名称

- [ ] **常量和配置**
  - [ ] 常量使用大写字母
  - [ ] 配置项有明确含义
  - [ ] 避免魔法数字和字符串

#### 2.3 注释和文档

- [ ] **代码注释**
  - [ ] 复杂逻辑有解释说明
  - [ ] 算法步骤清晰描述
  - [ ] 业务规则说明
  - [ ] 避免明显的注释

- [ ] **函数文档**
  - [ ] 函数目的清晰
  - [ ] 参数说明完整
  - [ ] 返回值描述准确
  - [ ] 异常情况说明

- [ ] **API文档**
  - [ ] 接口文档完整
  - [ ] 请求/响应示例
  - [ ] 错误码说明
  - [ ] 使用场景描述

## 审查结果处理

### 审查结果分类

1. **通过** - 代码质量良好，可以直接合并
2. **需要修改** - 存在一些问题，需要修改后重新审查
3. **需要重大修改** - 存在严重问题，需要大幅重构
4. **拒绝** - 代码质量不符合要求，不予合并

- [ ] 功能完整性：完整/基本完整/不完整
- [ ] 建议：通过/需要修改/拒绝

### 具体问题

## 常见问题及解决方案

### Q: 如何处理审查意见不一致？
A: 优先考虑功能性问题和安全问题，风格问题可以团队讨论统一标准。

### Q: 审查时间过长怎么办？
A: 重点关注核心模块和复杂逻辑，简单代码可以简化审查流程。

### Q: 如何平衡代码质量和开发效率？
A: 建立团队标准，通过工具自动化部分检查，关注关键质量问题。

### Q: 新团队成员如何参与代码审查？
A: 提供培训和指导，从简单代码开始，逐步增加审查复杂度。
